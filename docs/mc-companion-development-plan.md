# 大肥鱼管理中心与 Minecraft 陪伴插件开发方案

2026-11-18 · 设计基线 `3fa531e`，方案提交 `44a7a45`。用户已认可方案，授权从 G01 逐步实施至北京时间 23:00。各项是否完成以独立提交和实际验收证据为准。

**去山脚看看 → 发现石料 → 玩家授权采 16 块 → 实际带回河边**，是本方案的首个验收场景。玩家与大肥鱼各用自己的账号，在同一世界合作盖小屋。对玩家而言，管理中心和游戏里说话的是同一只大肥鱼。主 Agent 常驻管理中心，游戏子 Agent 是“她在游戏里的我”。采石任务结束后，这一局的陪伴仍可继续。

**建议先做两件事。** 用固定样本定下“看到、做到、带回”的判断，再用独立 Mineflayer 角色和可控服务器验证一块圆石的真实来路。主线成功用例要证明 16 块确实带回。平时只有某项不确定性影响下一步决定时，才打断玩家。管理中心把来源细节放在可展开的步骤里。

## 二、谁负责什么

玩家说“我们一起盖个小屋”，她先提议分工，双方谈妥后再自行安排。计划板记录每项约定的提出者和决定权。例如“备 8 块原木”若是玩家指定的数量，改建石屋时保留已采的 3 块并询问余量。若数量是她在“建材交给你”这项分工下的估算，她可以自行调整并写明原因。这个例子确定计划板语义，首个开发场景只需接通采石。

| 角色 | 拥有的职责 | 关键边界 |
|---|---|---|
| 主 Agent 与共享应用服务 | 主 Agent 理解共同目标、分工和改约，能主动询问子 Agent，也能在玩家从管理中心开口时作答。应用服务持有委托、来源身份、计划修订、待答问题和命令回执。 | 玩家明确绑定的目标、数量和地点由玩家修订。子 Agent 等答或行走时，主 Agent 仍能响应。查询进展只读。 |
| 游戏里的她 | 使用本次陪伴会话的上下文。选路线、查看可见岩壁、在游戏里提问、准备下一步、执行获准委托，能自然地向玩家报告或开玩笑。 | 路线可以自己改。采掘等新行动要有相应委托。谁在和玩家交谈，谁把问题问完。答复可来自另一入口。闲聊只有在玩家形成新约定时才改计划。 |
| MC 能力插件 | 可信原生 DLL 向宿主注册能力。游戏侧适配器用 Mineflayer 连接独立账号，负责聊天、观察、寻路、实际动作和停止。可控服务器另装只读观察端，为验收提供证据。 | 本体保持空插件可用。MC 账号、材料、地形和报告规则属于插件。服务端旁观证据仅供核验，游戏决策使用角色能取得的观察。 |
| 管理中心计划板 | 首页呈现当前目标、进展和需要玩家决定的事。任务详情按步骤展示玩家原话、主子通话、插件事实、计划变化、动作回执和主 Agent 的介入依据。 | 计划板通过共享服务发命令，执行结果由游戏回执和读回更新。显示主 Agent 最后确认的来源与时间。原话仅从授权详情读取，公开诊断继续无正文。 |

玩家启用陪伴、进入世界后，宿主可按设置唤起子 Agent。控制角色所需权限随委托授予。宿主保持一个角色控制者。玩家说“停，我来”或在管理中心停止时，游戏侧可立即停止接纳新动作并请求寻路、采集收尾，无需等待模型。板上分别显示停止请求和实际释放。断线、换世界、实例替换时旧行动绑定失效，迟到结果可更新原事实。同进程重连先重读游戏状态，效果未知的采掘不能自动重发。DLL 忙碌时沿用原有卸载约束。

## 三、首个场景如何验收

首例约定石料为圆石 `minecraft:cobblestone`，河边小屋选址为双方已知的会合区。目的地没有共同约定时，只追问缺少的地点。共同目标“小屋备料”下保留两个独立委托及其运行身份，第一项完成后结果继续可查。

| 玩家和大肥鱼经历的事 | 计划板的状态及凭据 |
|---|---|
| **去山脚看看。** 大肥鱼走到山脚，在可见岩壁发现石料。 | 查看委托完成，记录角色、世界、观察位置及采样。此时采掘调用数为零。 |
| **她在游戏里问“要我采一些带回来吗？”** | 游戏和管理中心显示同一待答问题。展开“为什么问”能看到发现石料的观察，以及原委托只授权前往查看。 |
| **玩家在游戏里答“采 16 块带回来”。** 跨入口变体在管理中心回答。 | 宿主核对玩家绑定、问题及相关计划修订，一次登记回答、关闭问题、建立新委托和待投递命令。显示“已授权，等游戏接收”。拒绝、过期、错误玩家或相冲突的另一份回答保持零新动作。 |
| **游戏接单、开始采掘、拾取。** | “已接单”来自命令回执，“正在开采”来自游戏动作。进度按本次自采入包计，原有库存、玩家赠物和重复报告单列。一次委托覆盖指定区域、物品、目标数量和返程，合法的每一步无需反复询问。执行前仍复核有效范围。 |
| **她带够材料返回河边。** | “已采够”与“返程中”分别有拾取和移动证据。同一角色在约定世界抵达会合区，并以到达时的新库存及本次来源记录核对数量，才显示“实际带回 16/16”。交入箱子属于另一种交付约定。 |

**数量不确定时怎样陪玩。** 严格验收核对本次来源。日常首页可以只说“我到河边了，身上有 6 块”。例如原有 5 块，自采 1 块，又捡到玩家给的 1 块，途中从混合堆里丢了 1 块。可确认她采得并拾取了 1 块、到场携带 6 块。能带回的自采量为 0～1。已知丢的是旧库存时，自采实带为 1。详情保留这种差别。普通盖屋可以继续。若短缺确实影响已约定的交付，先看能否在范围内补足，再决定是否问玩家。

## 四、消息、报告与介入

**本体统一业务消息。** 用版本化 JSON 表达消息编号、类别、陪伴会话、任务／委托、发送者、接收者、实际入口、回复或因果引用。对计划变更带期望修订，对游戏行动带实例、世界和命令身份。宿主从受信入口绑定身份。自然语言可提出意图，许可和回执由应用服务登记。模型 API 沿用现有角色。[模型消息](../model/include/dafeiyu/model_messages.hpp)

例如游戏子 Agent 提出问题 Q，管理中心收到玩家回答 A，计划板变更 R 引用 Q、A 和原查看委托，新命令 C 引用 R。游戏接纳和实际执行都回指 C。这样能查到“谁问、谁答、谁经手、发生了什么”。首版在宿主进程内对同一问题只采纳一次。重复投递复用原回执，相关委托已变更时重查原意。普通位置或背包更新只推进观察序号。已确认的决定即使尚未投递也可见。

首例中的“采 16 块带回来”同时给出数量和返程意图。应用服务用该答复建立绑定同一游戏实例、材料、区域、数量和目的地的新委托。后续具体工具候选匹配全部约束时复用这次决定，超范围的候选不能消费旧许可。若游戏聊天中有多个问题都能匹配一句“可以”，先问清指哪一项。

**插件注册游戏语义。** 登记当前世界、角色位置、动作和背包的快照及增量查询，声明可委托动作、完成回执、主动报告条件与证据引用。重要变化（发现目标、重大改道、影响交付的短缺、停下、断线、到达）及时报告。普通移动合并，主 Agent 可按插件约定的节奏读取。增量有缺口则补读快照。历史无法补齐时标明缺口。通报主 Agent 与打断玩家是两个决定。

| 返程或探索中的问题 | 主 Agent 的处理 |
|---|---|
| “你到哪了？” | 最近确认的地标和行动仍足以作答就直接回答，标明来源。对方要来会合、位置快速变化、信息过时或互相矛盾时，先读插件当前状态。需要解释选择再问子 Agent。断线只报最后确认位置。 |
| 连续三次返回同一坡脚 | 插件可报告三次独立移动、覆盖范围和新增观察。三条路线各查了新岩壁时继续探索。记录连续却没有新观察时，主 Agent 才询问受阻原因。时间线展示触发事实、询问、子 Agent 回答和随后验证。次数为场景样例。 |
| 玩家说“先别采了，过来看看” | 立即处理停止与改约，保留已采数量。明确说“看完接着采”时按约恢复。只说“先别采了”时等讨论结束再问。玩家曾限定“河边找”而要换搜索区时，在两处共用一个待答问题。 |

## 五、第一份真实游戏证据

在约定位置只挖一块，同时由另一玩家在脚边丢一块同种圆石。两份掉落在首次拾取前共存即可。客户端记录采掘目标、可见实体、拾取者和背包变化。服务端记录实际破坏者与方块、生成和丢弃来源、合堆方向、实际拾取与余量、位置及库存。按玩家／世界、在途动作与坐标、实体身份和各来源序号关联。跨进程时钟不假定同起点。回调可能被取消，须核实实际效果。[Mineflayer 拾取事件](https://github.com/PrismarineJS/mineflayer/blob/master/docs/api.md#playercollect-collector-collected) · [Paper 方块掉落](https://jd.papermc.io/paper/1.21.4/org/bukkit/event/block/BlockDropItemEvent.html) · [物品合堆](https://jd.papermc.io/paper/1.21.4/org/bukkit/event/entity/ItemMergeEvent.html) · [拾取余量](https://jd.papermc.io/paper/1.21.4/org/bukkit/event/entity/EntityPickupItemEvent.html)

| 对照样本 | 应有结论 |
|---|---|
| 未混堆。只拾取自采掉落 / 只拾取玩家丢物 | 自采入包分别为 1 / 0。均保留已破坏方块事实。 |
| 两份各 1 合堆，她全部拾取 / 两人各拾取 1 | 前者确认自采入包 1，后者只能确认 0～1。同一次拾取重报只算一次。真实分次拾取按可追溯余量累计。 |
| 原有 20，自己采 16 / 自己采 12 再获赠 4，均全部带回 | 最终背包同为 36，自采实带分别为 16 / 12。已确认自采途中损失 2 后用赠物补齐时，实带自采为 14。 |
| 同类物品混放、重连后原始记录缺失或到达前库存已陈旧 | 有上下界时显示范围，证据不足时显示“来源未核实”或“等待新观察”。只承诺能证实的数量。 |

把协议版本、客户端与服务器各自的原始记录、引用关系和预期结论一并留作阅读入口。Paper 文档提供候选观察点，真实合堆、部分拾取和返程归属待目标版本验证。严格验收在可控服务器开展。日常服务器缺少观察端时按可得证据显示，避免为普通游戏逐块加标签。

## 六、依赖和独立提交

以下每行交付一个可单独验证的行为。首个可审查提交是 G01。后续按直接前置接续。真实游戏探针可由固定本地命令驱动，早期即可做取证，随后再接正式主子会话。每步仅构建所需目标并运行定向检查。手写变更以含测试约 100～300 行为拆分参考，超出时沿该行的接口边界继续拆。每步独立提交，说明行为、验证、阅读入口和下一步，停下供审查。

| 单元 | 直接前置 | 单步交付 | 验收证据 |
|---|---|---|---|
| G01 场景样本 | 基线 | 固定四段主线、两项委托及来源对照 | 同样 36 块库存产生 16/12 两种正确结果。未授权、重复、缺口有明确预期。 |
| G02 双角色接入探针 | G01 | 在可控世界连入独立 Mineflayer 账号，固定兼容的游戏、库和服务端版本 | 区分两个玩家，读到角色位置、背包和会合区。记录版本与只读基线。 |
| G03 掉落来源探针 | G02 | 可控服务器只读记录破坏与玩家丢物，关联客户端的单块动作 | 同时同地两份圆石可分别追到她挖和玩家丢。取消或零掉落不记产出。 |

## 七、审查时值得决定的事

- **优先审计划板的完成判定。** 严格场景有足够证据才标记“自采并实带 16”。日常陪玩先报告对盖房有用的库存和位置，自采归属存疑时仅在会影响交付时询问。
- **首例把“带回来”落在已约定的河边会合区。** 玩家临时改约由新修订接管，旧目的地保留在历史里。会合区的几何边界和兼容版本组合由 G02 用小世界实测后记录。若某个版本无法提供所需证据，再讨论适配选择。
- **实施从 G01 开始。** 这份审查稿只覆盖一对主子会话及采石首例。完成一个小屋任务后的自主选目标、普适游戏能力和长期人格如何延续，可在首例验收后结合使用体验讨论。
