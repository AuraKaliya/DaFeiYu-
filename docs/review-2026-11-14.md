# 35 个提交的开发指导审查

审查范围：`c1ef0bc..07491b7`，共 35 个提交。审查起点工作区干净。依据开发指导检查功能边界、失败恢复、资源寿命、实际装配与测试覆盖；发现问题直接分项修复，阶段内只运行必要测试，最后统一全量验收。人工审查与先前自动验收记录分开保留。

## 已确认并修复的问题

### 1. 移除残留达到上限后不能继续恢复（P2）

来源：`3db3e54`，`package_remove.cpp`。旧实现收集第 65 个残留时直接失败；64 个旧残留加一次新的清理失败即可产生自身无法再次处理的状态。即使文件属性已经修复，重试仍在清理前被拒绝。

修复为每次最多持有和处理 64 个旧目录，明确报告尚有下一批；旧残留未清完时不再制造当前包的新残留，并保留当前包仍可见的状态。命令行不把“已清一批”误报为包已移除，失败路径仍显示具体残留。

旧行为是 `达到上限 → 抛错 → 一个也不清理`；现行为是 `处理首批 → 报告未完成 → 同一命令继续 → 最后移除当前包`。新增 65 个旧目录的回归先在旧实现失败，修复后 `plugins.remove`、`app.plugin_commands` 两项定向测试通过。

核心边界由直接拒绝：

```cpp
if (pending.size() == 64) throw std::length_error("package: too many removal remnants");
```

改为有界接纳并保留后续批次事实：

```cpp
if (pending.size() < 64) pending.push_back(entry.path());
else more_pending = true;
```

### 2. 批量关闭重复尝试同一个失败消费者（P2）

来源：`5565267`，`PluginManager::State::close`。原实现逐实例发起联动停止，相交依赖计划会多次包含同一消费者；一次关闭调用内就会再次进入已经报错的停止入口。新增真实 C DLL 计数回归确认旧实现调用两次，修复后只调用一次。

现在先合并消费者优先的完整计划、按具体实例去重，再执行各实例一次；独立分支仍继续收尾。已知批量停止失败不由管理器析构偷偷重试，未完成状态保留给明确重试。

### 3. 历史错误码误判本轮正常停止等待（P2）

来源：`61aadaf`，退出循环。实例的 `last_error` 按契约保留历史错误；停止失败后重试已经进入正常 Pending 时，旧循环仍因历史错误提前退出。

新增本轮关闭结果，入口依据实际本轮失败决定是否中止等待。真实 DLL 回归验证“失败 → 多次 Pending → 成功”，历史错误继续可查，但不再覆盖当前停止状态。仅运行 `plugins.manager`、`plugins.dependencies`、`plugins.instance` 三项相关测试，均通过。

### 4. 自定义安装限制在回滚和移除时丢失（P2）

来源：`b964482`、`3db3e54`。原安装接口允许明确的 `PackageLimits`，但回滚和移除重新使用默认限制；例如允许安装 33 层目录后，清理在默认 32 层处拒绝，造成自身接受的包无法正常结束生命周期。

现在暂存回滚沿用本次安装限制，独立移除接口也接受相同策略并贯穿检查和清理。App 默认限制保持不变。33 层真实目录回归在旧实现失败，修复后同时验证成功安装后的移除和非法配置后的完整回滚。

### 5. 授予后的域侧撤回可导致处理析构终止进程（P1）

来源：`101cfc4`、`3c772fe`。域控制器撤回已授予但未开始的请求时，将顺序状态设为 released；处理完成源只识别 cancelled，因而继续开始或析构时再次操作已经释放的顺序请求。回归在旧实现触发确定的进程终止。

现在独立保存域侧撤回首因，处理源通过推进或析构均能识别该事实，安全结算取消和实际退出；授予操作此前成功的事实不被改写。已绑定但未开始的请求也不能误用普通 finish 提前释放，须走明确撤回入口。仅运行顺序域、事件处理和 C 处理适配三项相关测试，均通过。
