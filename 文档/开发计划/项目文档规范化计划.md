## 立项理念与原始需求

用户审阅 MC 伙伴时，需要先知道哪些能力能用、哪些还要做，再决定读哪项证据。旧计划把能力清单、实施顺序、阶段记录、长期设想和操作说明放在一起，同一事项会得到两个答案。其他主题使用不同格式，读者还要重新学习查找方式。

按读者任务组织正文。审设计的人从一个入口找当前决定，排期的人先看到剩余交付，使用模块的人按操作目录查一次就能完成任务。每条事实明确由哪份文档维护。

## 目标与范围

覆盖仓库主线已有的 28 份 Markdown 及其代码、构建、测试、技能和分发引用。项目自有的设计、计划和说明使用中文文件名。根目录 `README.md` 作为仓库展示入口，`AGENTS.md`、`SKILL.md` 保留工具发现所用名称。第三方原始许可沿用原文及原名。组件程序名、协议、命令行参数和历史提交号保留原标识。

审阅者应能从首页查到一项能力的状态、其支持边界和证据，能区分已采纳待落地的设计与已有实现，能在脱离源码树的安装包里打开交付给该读者的说明。开发范围和优先级沿用各主题已有决定。

## 实施顺序与整体验收

1. **先定设计正文并清理冲突。** 以主线接口、运行入口和已采纳决定核对每个设计章节，分别记录保留、移入计划、退役或待核实。先保存有效约束再移除旧版。普通桌面与终端已共享常驻本体，专用 MC 宿主单独运行，据此可退役旧 UI 选型中关于进程的假设。冻结的 ABI v1 仍供兼容查阅。[宿主入口](../../apps/host/src/resident_entry.cpp) · [公开 v1 头](../../sdk/include/dafeiyu/plugin_abi.h)
2. **迁一个计划，再推广。** 用消息倒序、容器类型、创造模式评审和外部参考四个 MC 案例核对状态与证据。再按同一模板迁其他开发线。逐项以目标主线和验收核定状态，找不到证据的旧条目登记待核实及需要补查的来源。
3. **同一操作合并后再改名。** 按“读者、任务、参数”对照重复段落。保留各处独有的前提、选项（如终端 `/run --workspace`）、失败恢复、夹具散列和许可出处。移动与逻辑整理分提交。每批同步 README、技能、构建脚本和测试的引用。临时导航只给一个后继入口。
4. **逐批验证仓库与安装产物。** 检查中文文件名、相对链接和章节锚点，搜索旧路径直至所有在用消费者切换。当前四个安装输入分别对应 Runtime 的运行与第三方说明、桌面的 UI 验证说明和 SDK 的开发手册。依次用已构建的 Release 产物执行 `cmake --install <构建目录> --config Release --component Runtime --prefix <临时目录一>` 及对应的 `--component SDK --prefix <临时目录二>`。在两个临时目录打开手册，核对包内文件、内部链接与许可。已发布的入口若需兼容，从同一源安装或生成别名。[分发规则](../../cmake/Distribution.cmake) · [桌面安装](../../apps/desktop/CMakeLists.txt) · [SDK 安装](../../sdk/CMakeLists.txt)
5. **以读者问题作最终抽验。** 从根入口找到共享本体的设计理由。在 MC 计划首页判定“独立待答、大箱、创造取物”三项各属何处。在其他三份计划定位下一项及通过条件。从发布包按目录找到可执行的命令。检查每个主题只保留一份当前正文、每个计划项只出现一次、每条完成记录可还原到主线证据。抽验通过后收起过渡导航。

每批交付列出旧文件及章节、新归属、退役依据、定向验证和下一项。读者发现遗漏时可用基线提交及原路径取回原文。某一批需要调整时可单独回退该批。
