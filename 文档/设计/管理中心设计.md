# 管理中心设计

管理中心是常驻本体的受信客户端。桌面在有消息循环的 STA 线程上持有 Win32 窗口与 WebView2，普通聊天终端可连接同一本体。业务线程持有 `Application`、主会话、SQLite 和插件实例。客户端只交换有界的命令、回执和值快照。核对基线为主线 `8fce20e`。[窗口入口](../../apps/desktop/src/main.cpp) · [管理服务](../../apps/host/src/management/host.cpp) · [系统架构](项目架构设计.md)

## 界面与事实归属

空插件时侧栏有「房间」和「设置」。房间中央显示本体、身体位置、最近变化和只读信箱，右侧显示带时间的聊天及发送栏。切到设置时使用整块内容区，返回后续读原会话。「最新状态」显示来源和修订，「最近变化」只记录本窗观察到的变化。断开时保留旧样本并显示过期，重新取得快照后建立新基线。读房间或打开信箱都可在没有模型调用的情况下进行。[正式面板](../../apps/desktop/web/src/MainPanel.vue) · [双窗场景](../../tests/desktop/ui_history_windows.ps1)

| 要展示的内容 | 权威来源与界面边界 |
| --- | --- |
| 聊天与队列 | 本体持有主会话、命令结果及持久消息。窗口维持自己的游标、焦点与未发送草稿。增加本轮输入、排下一轮、停止当前轮使用各自的宿主回执。 |
| 房间与信箱 | 房间和各邮箱发布只读视图。窗口可重新同步，而消息消费、回复与角色感知由原服务负责。[书房](内置书房设计.md) |
| 目录与运行实例 | 磁盘扫描反映已安装包，活动实例由插件管理器掌握。操作回执按原后台、包、代次和提交身份查回。 |
| 配置 | 主体用户文件、插件包默认值及各插件的用户覆盖由对应所有者维护。界面可保存草稿，明确显示已保存值与实际运行值。业务层逐字段校验完整批次。 |

可信主文档可取得本会话正文。公开 `state.read` 只返回运行摘要，探针或独立 Frame 不得读取主会话正文。宿主按实际文档、Frame 及视图代次绑定权限。窗口事件中避免同步等待业务或重入 WebView2 消息循环。[原生桥接](../../apps/desktop/src/host/probe_host.cpp) · [受限快照](../../apps/desktop/tests/ui_run_status_probe.cpp)

## 主聊天与信箱

后台写入 `main-conversation.sqlite3`。逻辑会话与持久消息号可跨启动读回，原活动回合、窗口与插件实例另有身份。普通发送、追加、排队从同一聊天渠道按意图分派。库中的正文和投递历史独立于内存中最近 16 轮、2 MiB 的显示窗口。清空运行上下文、关闭 Trace 或重建窗口后仍能分页读取。[主聊天存储](../../apps/host/src/main_messages.cpp) · [重启与恢复](../../apps/host/tests/message_recovery.cpp)

### 消息、回执与分页

已握手的客户端通过既有本地管道的 `op=request` 发送业务请求。`body` 共用 `version:"1"`、`type` 和窗口自定的 `request`。回复回显 `request`，包含逻辑会话号 `conversation`、原后台 `instance` 和采样时的 `watermark`。消息号、游标、水位和修订号均为十进制字符串。[管理分派](../../apps/host/src/management/message_protocol.cpp)

| 业务请求 | 附加字段 | 成功结果 |
|---|---|---|
| `messages.subscribe` | 无 | `messages.subscribed`。为当前窗口登记订阅并取得已提交水位。后续 `dialogue.read` 的 `messageWatermark` 可提示补读，即使对话显示修订未变也会返回。重连须重新订阅。 |
| `messages.read` | `conversation, direction, cursor, through, limit` | `messages.page`。固定订阅取得的 `through`，整数 `limit` 取 1～64。`history` 按消息号倒序，从 `cursor:"0"` 取最新一页，回执为该水位时的版本。`changes` 按修订正序，读取 `(cursor, through]`。有后页时用 `next` 续读，`more` 为假时结束。 |
| `messages.receipt` | `conversation, source, submission` | `messages.receipt`。返回原提交的最新 `record`，未找到为 `null`。 |

记录包含稳定的 `message`、本次 `revision`、宿主 UTC 毫秒时间 `utcMs`、`source`、`submission` 和该修订的 `receipt`。窗口按逻辑会话和消息号更新同一行，一页实际交付后再保存游标。多窗读取互不消费。数据库位于数据目录下的 `main-conversation.sqlite3`。[双窗口与断点验收](../../apps/host/tests/message_protocol.cpp)

新追加和待发项在入库前按已发布的原回合、条数和字节余量检查，分派时再核对当前条件。已结束回合的追加返回 `stale`，超出对应容量返回 `full`。这两种预先拒绝的提交没有 `storedMessage`。单页还受字节预算约束，即使记录数小于 `limit`，只要 `more` 为真，窗口就按 `next` 继续读取。

提交正文沿用 `dialogue.submit`、`dialogue.append`、`dialogue.enqueue`。窗口在第一次发送前生成并保留 `submission`（1～128 个 UTF-8 字节），三种请求仍带原有的 `command` 和 `text`。追加、排队另带订阅返回的 `instance` 及原 `session`、`turn`，也可附来源时间 `sourceUtcMs`。同一 `submission` 重试时保持原字段值。新连接使用自己的 `command` 空间，可用 `messages.receipt` 按 `source:"desktop"` 与原 `submission` 复查。相同提交号改动原文、去向或目标会返回 `conflict`。

成功入库后，命令回执附加 `storedMessage`。它是持久消息号，原 `message` 仍表示回合内补充号或待发项号。初始持久回执为 `pending`，开始交付前写为 `dispatching`。已接纳的新回合为 `accepted`，追加等待带入为 `waiting`，待发项为 `queued`。终端正文来源为 `terminal`，沿用同一持久库。[后台接纳与回执](../../apps/host/src/main_messages.cpp)

原窗口以同一 `command` 再读 `dialogue.read` 或重发相同提交，都按已绑定的 `storedMessage` 返回最新命令结果。写锁解除后，原窗口和用同一 `submission` 重连的窗口可分别查到实际接纳。持久回执中的 `submitted` 附带实际的 `modelStep`，`removed` 保留已移除的待发项，`unknown` 表示原交付实效仍待核对。[写锁与重连验收](../../apps/host/tests/message_recovery.cpp)

直接对话和原生书房点名产生的非空白最终文本进入主聊天。普通结构化对话还可调用 `main_reply({"text":"…"})` 提前发言或追问。成功回执的 `delivery` 和 `message` 分别标识本次投递和已写入的消息。同一回合末尾再次给出已显式发过的相同文字时复用原投递。独立回合、不同显式调用各有自己的投递号。内部入口的结算、工具回包和纯空白结算保持在原路径。[输出适配器](../../apps/host/src/main_output.cpp) · [送模记录与渠道回执验收](../../apps/host/tests/persistent_dialogue.cpp)

发言首次写入后，在线终端即可读到正文，回合仍可继续运行。旧窗口的回合快照同步最近一条已写入的发言，持久历史保留每条发言。终端批处理读到 EOF 时，会等待自己发起的回合和待写答复。若持续无法写入，它以失败退出并显示原投递号，后台继续按该号补写。[正式终端验收](../../tests/application/terminal_entry.ps1)

### 信箱的只读视图

已握手的管理窗口沿用本地管道的 `op=request`。首次可发送 `{"version":"1","request":"dir-1","type":"mailbox.list"}`。回包的 `event` 为 `mailbox.directory`，回显 `request`，并带有后台 `instance`、目录 `revision`、采样时刻 `sampledUtcMs`、`state` 和 `sources`。绑定后的请求可附 `instance`，与当前后台不符时返回 `stale` 和空来源表。

每个来源有 `id`、`label`、`kind`（`builtin` 或 `plugin`）和字符串 `generation`。插件来源另带包标识 `plugin`，`label` 取自该运行代次加载的清单显示名。刷新磁盘包目录后，当前代次仍显示原名，重载才使用新名。主聊天、书房和实际接入信箱的各插件分别占一个来源。插件双向地址和它登记的主 Agent 业务地址归同一代次。窗口应保存服务端给出的来源 `id`，卸载后重新加载同包会签发新的来源。目录修订随地址绑定及撤销改变。读取已发布的目录不会触发收件或模型调用。[宿主投影](../../apps/host/src/mailbox_view.cpp) · [管理分派](../../apps/host/src/management/mailbox_protocol.cpp)

目录请求在绑定 `instance` 后也可加 `revision`。该目录修订仍有效时返回原样本，地址已经改变则返回 `stale` 和空来源表。

`{"version":"1","request":"box-1","type":"mailbox.read","instance":"原后台","source":"目录给出的 id"}` 返回 `mailbox.snapshot`，回显原请求、后台及来源，并给出来源自己的 `revision`、`sampledUtcMs`、`state`、`mailboxes` 和 `messages`。同一份采样可由多个窗口重复读取。该来源入箱、实际取件或地址绑定改变才更新来源修订，其他来源可继续沿用原采样。编号、修订及累计水位使用十进制字符串，UTC 毫秒和分类版本使用 JSON 整数。

每封信的 `id` 由原信箱与序号组成，作为不透明字符串保存。`category`、`categoryVersion` 给出分类，`direction` 为 `toHost` 或 `toPlugin`，`state` 为 `pending` 或 `received`。嵌套的 `receipt` 带有原 `mailbox`、`sequence`、`acceptedUtcMs` 和 `acceptedRevision`。回执最初为 `state=accepted`，原接收方实际取走后才出现 `state=received`、`receivedUtcMs` 与 `receivedRevision`。原生载荷缺少可公开的分类名时，`category` 为空字符串。业务正文留在原系统。回信在自己的目标信箱中有独立编号，可分别观察入箱与实收。

消息按最近入箱顺序返回。每个地址另列 `id`、`direction`、累计 `accepted`、累计 `received` 和最早保留序号 `firstRetained`（无记录为 `"0"`）。后台保留全部待收信及有界的近期回执。窗口可在原请求加 `message` 查一封详情，加 `revision` 核对所见版本。当前有效的空来源返回 `ready` 和空信件表。后台或来源失效、指定修订已变、选中信件已离开保留区间时返回 `stale` 和空信件表。读取失败沿用 `management.error`。取得新目录及当前来源快照后可重新选择原件。[原生收发回执](../../modules/events/src/mailboxes.cpp) · [管理信箱验收](../../tests/plugins/management_mailboxes.cpp)

## 插件管理与设置

打开设置仅从后台已发布的目录读取。用户可请求加载、卸载已安装包，观察操作号、受理、等待和实效。插件可写设置以及在设置页安装或移除包分别按计划接入；终端已有的安装路径可在操作手册查阅。[管理中心开发计划](../开发计划/管理中心开发计划.md#待办) · [构建与运行说明](../使用说明/构建与运行说明.md)

### 包、代次与操作回执

初次查询发送 `{"version":"1","request":"p1","type":"plugins.list"}`。已握手窗口可指定 `instance`，并以 `revision` 核对原目录。响应 `plugins.directory` 回显请求，带有后台实例、十进制字符串修订、`ready` 或 `stale`、`packages` 和无效目录项数 `unavailableCount`。旧后台或旧修订返回空行集和 `stale`。有效空目录返回 `ready`。根目录扫描失败按管理错误上报。读取只使用业务线程已发布的目录。

每行有包 `id`、`name`、`version`、`installed`、`loaded`、`generation`、`state`、`canLoad` 和 `canUnload`。`installed` 表示最近一次成功扫描可发现该包，`loaded` 表示宿主仍持有具体实例。代次为十进制字符串，无实例为 `"0"`。状态为 `installed`、`active`、`stopping` 或 `failed`。有实例时另带实际加载的 `loadedName`、`loadedVersion` 和 `errorCode`，磁盘包已移出目录时仍列出其运行责任。操作字段表示可以提交，实际执行仍复核依赖、忙碌和停止状态。[业务目录](../../apps/host/src/management/plugin_directory.cpp) · [双管道验收](../../tests/plugins/management_plugins.cpp)

已安装包的加载请求形如 `{"version":"1","request":"w1","type":"plugins.load","instance":"原后台","command":"1","id":"test.directory","revision":"原目录修订","generation":"0"}`。每个已握手窗口的插件命令独立从 `"1"` 连续递增。宿主返回 `plugins.operation`，初始 `state=queued`、`effect=unconfirmed` 和不透明的 `operation`。窗口可发送 `{"version":"1","request":"q1","type":"plugins.receipt","instance":"原后台","operation":"原操作号"}`，重新连接也能查询。

两个写入口均接受可选 `submission`。页面在首次提交前生成并保留 UUID，例如 `3b75faab-3207-4b0a-ae38-e7a7c0e96ada`，同时保留原 `instance`。此时操作号固定为 `plugin/request/3b75faab-3207-4b0a-ae38-e7a7c0e96ada`，第一次回包丢失或关窗时，新窗口可直接用 `plugins.receipt` 查询。公开标识允许 1～96 个 ASCII 字母、数字、连字符、下划线或点。回执回显原 `submission`。提交省略该字段时沿用原窗口命令水位和宿主签发的不透明操作号。

原窗口重用同一 `command` 必须保持完整意图及 `submission` 一致。同一公开提交号改动作、包、修订或代次返回 `conflict`。另一窗口读回原件、或以相同意图命中已接纳记录，均只返回原回执，不占用该窗口的命令号。详细回执退休后，公开提交号在原后台仍返回 `expired`，重复提交也不会执行。未见过的操作号返回 `unknown`，重启后按旧后台身份查询返回 `stale`。[首包丢失与重连验证](../../tests/plugins/management_plugin_recovery.cpp)

操作回执带有原 `command`、`action`、`id`、`revision`、`targetGeneration` 和核实的 `generation`。实际成功加载为 `succeeded/loaded`，有底层返回码时提供 `nativeCode`。同一窗口重发原命令可读回原结果，改目标或参数返回 `conflict`，跳号返回 `outOfOrder` 和 `expectedCommand`。旧修订或代次返回 `stale/notApplied`。同一后台有界保留 64 项，进行中的记录受保护，已退休的命令号返回 `expired`。原操作号已不可查时返回 `unknown`。[业务线程与原操作回执](../../apps/host/src/management/plugin_actions.cpp)

`plugins.unload` 使用相同信封和连续命令号，`generation` 必须取原目录行的非零代次。宿主按默认依赖保护卸载本包。若工作忙碌或有代码、依赖持有，原回执分别是 `busy/retained` 或 `inUse/retained`，实例继续存在。原管理器已受理但尚未退出时为 `pending/stopping`。DLL 已关闭而该代次仍有排队的宿主工作时，也保持该等待状态。同一操作号确认原代次实际回收后变为 `succeeded/unloaded`，`nativeResult` 保留初次调用的 `pending` 或 `closed`。生命周期失败返回 `failed/retained`。显式重试使用当前目录和新命令号，原操作持续反映其自身结果。

加载时若依赖尚未激活，或系统未能打开清单指定的 DLL，宿主按实际持有的代次结算。确认未创建实例时回执为 `failed/notLoaded` 和 `generation="0"`。生命周期已经返回状态码时附 `nativeCode`。卸载因依赖占用或停止失败而保留的原回执，在后来显式重试成功后仍可按原号读取。[依赖、停止失败和模块打开验证](../../tests/plugins/management_plugins.cpp)

### 本体设置与保存

已连接窗口发送 `{"version":"1","request":"s1","type":"settings.read","owner":"host","instance":"原后台"}`。可带上次读到的十进制字符串 `revision` 核对同一版本。`settings.snapshot` 回显请求、所有者与后台，给出已保存的 `revision`、运行中采用的 `appliedRevision`、待重启标记 `pendingRestart` 和当前服务的写入能力 `canSave`。旧后台或旧修订返回 `state=stale` 及空字段表。主体尚无供应商配置时返回 `unavailable`。

就绪时 `fields` 返回 `provider` 和 `timeout_ms`，每项携带 `id`、`type`、`access_mode`、`source`、已保存的 `value` 和运行中的 `appliedValue`。供应商只读。超时允许 1～600000 毫秒的整数，来源为启动配置 `startup` 或主体用户覆盖 `user`。正式常驻入口启用保存，独立注入配置的应用可通过 `canSave=false` 表明只提供读取。后端只投影这两个字段。[主体字段投影](../../apps/host/src/management/settings_protocol.cpp)

保存示例为 `{"version":"1","request":"s2","type":"settings.save","owner":"host","instance":"原后台","revision":"1","submission":"window-a-1","changes":{"timeout_ms":5800}}`。`revision` 使用窗口所见的已保存修订，`submission` 由窗口为本次意图生成，最多 96 个 ASCII 字母、数字、点、斜杠、连字符或下划线。主体用户文件为数据目录下的 `host-settings.json`，采用同目录临时文件完整刷新后原子替换。首次读取沿用启动配置，首次保存才创建文件。

`settings.result` 的 `state=saved` 表示已落盘，`savedRevision` 和 `savedValue` 对应该次提交，`revision`、`appliedRevision` 和 `pendingRestart` 对应当前状态。下次正式启动在创建会话前采用已保存的超时。只读字段使整批返回 `readOnly`，未知字段或越界值返回 `invalid`，两窗基于同一修订保存时后到者返回 `conflict` 和当前修订。磁盘发布失败返回 `failed`，文件在运行期间被外部改写时返回 `storageChanged` 并保留现场。

同一意图可按原提交号重读。窗口发送 `{"version":"1","request":"s3","type":"settings.receipt","owner":"host","instance":"当前后台","submission":"window-a-1"}` 查询最近 32 次成功保存的原回执。以相同基准修订和相同值重发原提交会返回原保存修订，改值或改基准返回 `submissionConflict`。重启后用新后台身份仍可查原提交，超出保留范围或从未成功写入的提交返回 `unknown`。[保存与冲突裁定](../../apps/host/src/host_settings.cpp) · [文件发布](../../apps/host/src/host_settings_file.cpp) · [双窗、写锁与重启验证](../../apps/host/tests/management_settings.cpp)

正式入口验收在同一用户目录先后启动两个 `dafeiyu-host.exe` 进程，分别持有原进程句柄并核对退出码。首次启动从指定配置取得超时，保存后另一个窗口仍可读到旧采用值。新进程采用用户覆盖，也能复查原保存回执。两次启动期间主会话均保持空闲。[正式本体验收](../../apps/host/tests/resident_settings.cpp)

### 插件公开设置

窗口从 `plugins.list` 选择一个活动包，记录包的 `id`、`generation` 和后台 `instance`。活动行的 `hasPublicSettings=true` 表示该代次已登记可读字段。请求示例为 `{"version":"1","request":"ps1","type":"settings.read","owner":"plugin","instance":"原后台","id":"test.public-settings","generation":"原代次"}`。可加上次返回的 `revision` 复核原快照。[服务端读取](../../apps/host/src/management/settings_protocol.cpp)

`settings.snapshot` 回显 `owner`、`instance`、`id`、`generation` 和 `request`。就绪时 `state=ready`，`fields` 逐项给出 `id`、`type=string`、`access_mode=read_only`、`source=default|user`、`value` 和 `appliedValue`。两项值均取当前实例创建时真正采用的有效配置。该快照固定到代次，`revision` 与 `appliedRevision` 均等于代次。文件编辑在重新加载后才进入新代次。

活动包无声明返回 `notDeclared`。后台、包、代次或修订不匹配时返回 `stale`。公开声明无效、字段类型不匹配或实例正在停止时返回 `unavailable`。这些状态均带空 `fields`，读口的 `canSave` 为 `false`。测试包仅登记 `displayName`，同一配置中的其他键保留在业务实例中。[测试插件声明](../../tests/fixtures/public_settings/ui/manifest.json) · [双管道、覆盖来源与重载验收](../../tests/plugins/management_plugins.cpp)

## 进程退出与软件日志

关闭一个窗口只释放该视图。设置、托盘或终端显式请求退出时，目标是原本体实例。窗口在握手时取得命名管道对端的同步进程句柄及退出意图事件。收到 `stopping` 时显示收尾；读到原进程的正常退出码才进入本窗 WebView2 回收流程。首包丢失可通过已持有的事件核实原意图。同目录若出现替代实例，继续观察原句柄，避免误停新本体。[原实例观察](../../apps/host/src/management/resident_watch.cpp) · [多窗退出](../../tests/desktop/ui_resident_exit.ps1)

本体持有通知区图标，恢复已有窗口或从本体目录启动管理中心，任务栏重建时恢复图标。无交互桌面或注册失败时，本体的业务仍能工作，实际结果记入软件日志。普通轮询汇总状态变化与首末错误。后台、窗口和普通终端各按进程启动实例写日志，记录 UTC、相对时间、序号、PID 和结果；原退出操作号关联请求、收尾阶段与外部看到的退出。日志独立于 Agent Trace，按分段与目录预算轮换。[托盘实现](../../apps/host/src/resident_tray.cpp) · [软件日志](../../apps/host/src/software_log.cpp) · [真实进程验收](../../tests/desktop/ui_resident_windows.ps1)

## 已采纳的扩展设计

以下是管理中心步骤 7 未交付部分及步骤 8 的实现目标。当前的公开读口与正式可写字段在上一节列明。容量初值、UI 提供方 C 结构及窗体细节需要在其实施单元冻结。[管理中心开发计划](../开发计划/管理中心开发计划.md#待办)

**配置和插槽。** 插件定义字段类型、约束及有效的 `read_only` 或 `writable` 模式。宿主按基准修订校验整批变更，在用户目录保存覆盖。插件实际采用新值以成功重载和新代次为准。组件可在开放的插槽追加或替换，插件还可登记板块和窗体。追加按稳定贡献身份排列，替换发生冲突时拒绝整个批次，撤销时恢复宿主默认组件。默认信箱来源可独立于 UI 注册。[插件配置装配](../../modules/plugin_host/src/config.cpp)

**声明式组件。** 包的 `ui/manifest.json` 与现有 `plugin.json` 及原生 ABI 分版，发现只读元数据。描述包含插件身份、所需能力、贡献、渲染方式、绑定、动作、允许范围、放置位置和回退。组件身份、名称及版本稳定，输入与动作绑定已登记的契约。字段路径按 JSON Pointer；开关条件只支持有界比较与逻辑组合；组件树不执行插件表达式。用宿主组件渲染文本、图标、表单、分页和业务摘要。草稿在显式保存时提交，宿主执行口复核权限与当前现场。

**协议与预算。** 视图应能按目录查询、订阅／重同步、按号查询或取消已接纳操作、分块读写临时文本。拟定的能力族包括 `ui.catalog.read`、`state.open/read/close`、`action.invoke/read/list/cancel`、`resource.read/upload/release`。请求按视图及代次绑定，有界回执保留在途操作；重投查原回执，参数冲突或过期均明确返回。候选预算分别为每包描述 256 KiB、8 个页面／4 个摘要／4 个房间入口，每页 256 个节点／12 层，每视图各 8 个订阅与普通请求，每桥接会话 32 个在途及 64 个终态回执。状态消息 256 KiB，进程内最多 64 个临时资源且合计 16 MiB，单块原文 16 KiB。取消和关闭须留控制空间。这些数值用于实现时验证，具体业务上限优先。

**窗体、自定义页与卸载。** 同一贡献可在内嵌弹层及独立 Win32 窗体中展示，两路订阅同一实例，各有视图身份。自定义页使用独立来源、有 sandbox 的 iframe，仅从已校验的包资源根加载。宿主校验实际 Frame、实例及视图代次、大小和参数，导航或关闭时撤销授权。不向页面开放凭据或原生句柄。可选提供方计划通过 `dfy.ui.provider@1` 协商。业务线程调用并复制描述，发布注册目录后窗口才可见。卸载预检待退工作、依赖和草稿，停止新接纳、分离 UI 回调、归还其代码凭证，等原工作与模块实际退出后移除对应贡献。失败保留原实例及可复核的状态。[Frame 来源约束](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox) · [现有插件管理器](../../modules/plugin_host/src/manager.cpp)
